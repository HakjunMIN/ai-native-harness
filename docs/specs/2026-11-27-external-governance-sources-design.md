# 기존 업무 시스템의 승인된 결정을 프로젝트 거버넌스에 적용하기

상태: 2026-11-27 설계 승인. 단독 호출 범위를 포함한 문서를 확인한 뒤 구현 계획 작성을 승인했다. 구현·배포 승인은 별개다.

## 목표와 확인한 선택

대상은 이미 Confluence, Slack, Jira에서 일하는 프로젝트 팀이다. 하네스가 새 티켓을 계획할 때 팀이 이미 내린 결정을 찾고, **현재 작업에 유효한 규칙과 과거 작업에만 허용된 예외를 구분**해야 한다. 사람에게 같은 결정을 다시 내려 달라고 요구하지 않는 것이 목표다.

1. **공식 출처 인정:** 지정된 출처에서 권한 있는 소유자의 승인과 적용 범위가 확인된 결정은 저장소에 옮기거나 재승인받지 않고 적용한다. 출처를 프로젝트 표준으로 승격하는 별도 절차를 모든 결정에 요구하지 않는다.
2. **프로젝트별 출처 목록 + 작업별 조회:** 온보딩 때 공식 출처와 범위를 확인한다. 매 작업에서는 관련 원문만 읽는다.
3. **SDLC와 단독 호출 모두 적용:** 프로젝트 결과물을 설계·변경·검토하는 스킬은 호출 경로가 달라도 동일한 프로젝트 표준을 적용한다. 순수한 제품 사용법 설명까지 팀 자료를 검색하는 것은 목표가 아니다.

검색 결과, 최근 메시지, 이모지 반응, 티켓의 `Done` 상태만으로 정책이 결정되면 실패다. 외부 자료는 읽을 데이터이지 에이전트 지시나 도구 실행 권한이 아니다. 승인된 규칙을 **발견**하는 것과 새 규칙·예외를 **승인**하는 것은 다르다.

## 검토한 접근

| 접근 | 장점 | 한계·선택 이유 |
|---|---|---|
| **공식 출처 목록 + 필요 시 조회 (선택)** | 기존 업무 도구에 원본을 두고 티켓에 링크되지 않은 결정도 찾을 수 있다. | 프로젝트별 출처 소유자 확인과 실행 시 읽기 권한이 필요하다. |
| 티켓·저장소 링크만 따라가기 | 별도 온보딩이 거의 필요 없다. | 링크되지 않은 기존 표준을 놓쳐 팀에 다시 묻게 된다. |
| 별도 검색 인덱스에 동기화 | 넓은 자료를 빠르게 검색할 수 있다. | 권한 회수, 삭제, 복제본의 최신성까지 운영해야 한다. 현재 목표에 필요하지 않다. |

## 제안하는 운영 방식

**온보딩.** `sdlc-setup`이 프로젝트 표준 색인, ADR, 기존 안내 문서와 그 안의 링크에서 후보를 먼저 찾는다. 목록은 대상 프로젝트의 기존 표준 색인 또는 거기서 연결한 프로젝트 소유 문서에 둔다. `AGENTS.md`에는 읽기 위치만 둔다. 소유자가 확인한 행만 사용하며, 한 행에 출처 ID, 허용된 읽기 범위(공간·페이지·채널·프로젝트 등), 관할 주제/모듈, 결정 소유자와 인정할 승인 기록, 목록 확인 근거를 남긴다. 공간 전체를 등록해도 공간 내 모든 문장이 승인되는 것은 아니다. 목록 추가·권한 범위 확대는 담당자가 확인할 변경안으로 제시한다. 등록은 원격 접근권한을 부여하지 않는다.

**조회.** Discovery에서 영향받는 모듈·변경 유형을 목록과 대조한다. 해당 실행 주체가 이미 사용할 수 있는, 인가된 읽기 도구의 기능과 범위를 먼저 확인한다. 직접 식별자가 있으면 원문을 열고, 없으면 허용된 범위 안에서만 검색한다. 조회 범위를 제한할 수 없으면 광역 검색으로 대체하지 않는다. 결과 요약이나 링크된 타 공간은 공식 결정으로 간주하지 않는다. 소유자, 승인 대상, 상태, 적용 범위, 대체·만료 여부를 실제 기록에서 확인한다. 공식 기록 자체가 외부의 승인 근거를 가리키면 그 근거도 허용된 권한 안에서 확인한다.

**판단.** 현재 범위에 유효한 승인 기록은 직접 적용한다. 논의·제안은 배경이며 기준선에 올리지 않는다. 예외는 해당 규칙의 소유자가 승인한 대상과 기간·종료 조건 안에서만 적용한다. 권위는 제품명이 아니라 **주제별 소유권과 확인된 승인**에서 나온다. 로컬 ADR과 외부 기록도 같은 원칙으로 비교한다. 명시적인 대체 관계나 범위 차이로 해소되지 않는 충돌은 어느 쪽이 최신인지로 결정하지 않는다. 중요한 규칙이 확인되지 않으면 출처와 쟁점을 한 번에 제시하고 해당 결정에 의존하는 작업만 보류한다.

**기록과 재확인.** Discovery에는 적용 규칙과 미해결 쟁점을, `02-plan.md`의 Project baseline에는 적용 규칙 요지·범위, 출처 ID와 문서/결정 식별자, 소유자·승인 근거, 확인 시각, 판본을 남긴다. 외부 문서에 Git 커밋을 꾸며 넣지 않는다. 판본이 없으면 같은 항목을 다시 비교할 수 있도록 관련 규칙과 승인·범위·상태 필드의 내용 해시를 쓸 수 있다. 해시는 변경 비교용이지 승인 증명이 아니다. 검토·검증·재개 시 해당 출처 목록과 적용 항목을 다시 비교한다. 관련 없는 편집은 영향 없음으로 기록하고, 요구사항이나 정책의 실질 변경은 기존 G1/G2 재승인 규칙을 따른다. 승인된 계획은 이력 보강을 이유로 덮어쓰지 않는다.

**스킬로 전달.** 현재 고객용 스킬 37개 중 11개가 `project-governance.md`를 직접 가리키고, 37개 모두 `principles.md` 또는 `protocol.md`를 참조한다. 이 두 공통 진입점에 같은 적용 기준을 연결한다. SDLC에서는 단계 담당자가 관련 규칙·범위·예외를 선별하고, 기술 스킬은 인계받은 기준선을 적용한다. 단독 호출에서는 최초 담당 스킬이 프로젝트의 표준 색인과 해당 범위의 소스 목록을 확인하고, 허용된 결과를 하위 스킬에 전달한다. 같은 작업·권한·범위에서 중복 조회하지 않는다. 하위 작업의 범위가 넓어져 기존 근거로 판단하지 못하면 담당자에게 추가 확인을 돌려보낸다. 단독 호출 결과에는 적용 규칙과 공유 가능한 근거 또는 확인 한계를 남기되 티켓·상태·게이트는 생성하지 않는다. 프로젝트 표준은 기술 스킬의 공식 제품 문서 조회를 대체하지 않으며 제품 문서에 사내 데이터를 보내지 않는다.

**권한과 저장.** 소스 열람 권한과 대상 저장소에 정보를 남길 권한은 별개다. 프로젝트가 저장해도 된다고 확인한 최소한의 참조와 판단 결과만 남긴다. 채널 대화·문서 본문·첨부의 일괄 복사, 토큰 저장, 사용자 대신 권한 요청·설치·설정 변경은 범위 밖이다. 식별자·제목·판단 요약 자체도 노출하면 안 되는 경우 원격 내용을 산출물이나 다른 에이전트에 전달하지 않는다. 필요한 경우 소유자가 해당 독자에게 공개 가능한 결정 참조를 제공할 때까지 그 판단만 보류한다. 게이트의 증거는 계속 실행 디렉터리 안의 승인 대상 산출물이다. 원격 링크를 증거 파일로 대체하지 않는다.

## 기존 동작과 경계

- 출처 목록이 없는 프로젝트는 현재의 저장소 기준선을 그대로 사용한다. 외부 도구가 없어도 로컬 작업을 시작할 수 있다. 단, 적용 대상으로 등록한 규칙을 현재 확인할 수 없을 때에는 ‘규칙 없음’으로 처리하지 않는다.
- Jira에서 프로젝트 결정을 읽는 것과 `jira-sync`로 특정 티켓을 접수·갱신하는 것은 별개다. 로컬 요청을 Jira 티켓으로 바꾸거나 Jira outbox를 만들지 않는다. 세 시스템 모두 이 기능에서는 읽기 전용이다.
- 첫 버전은 기존 권한·읽기 도구를 사용하는 하네스 절차다. 신규 커넥터, 자격증명 관리, 상시 수집, 전사 검색, 정책 자동 작성, 새로운 강제 게이트나 상태 스키마는 만들지 않는다. 실제 도구 가용성은 호스트별로 구분해 보고한다.
- 변경 지점은 `project-governance`, setup·discovery·plan, 기준선을 소비하는 review·verify·resume 및 handoff 안내다. 기존 `harness.lock.json`으로 고정된 티켓은 원래 동작을 유지하고, 과거 실행에 새 기준선을 소급 작성하지 않는다. 새 프로젝트에서도 출처 목록을 도입하지 않으면 외부 조회를 요구하지 않는다.
- 세부 표 형식, 제품별 읽기 도구 선택, 내용 해시 정규화 형식은 구현 계획에서 정한다. 승인된 설계를 적용하기 전에는 라이브 시스템에 연결하거나 소비 프로젝트를 수정하지 않는다.

## 인수 사례

| 상황 | 기대 결과 |
|---|---|
| 저장소에는 없는 공식 배포 절차가 Confluence에 있고 이번 릴리스에 적용됨 | 새 정책 승인을 요구하지 않고 관련 절차와 승인 판본을 계획에서 식별할 수 있다. |
| Slack에서 절차 생략을 논의했고 Jira에는 지난 릴리스 한정 승인만 있음 | 이번 릴리스는 기본 절차를 따른다. 논의와 지난 예외는 현재 예외가 아니다. |
| 지정 Slack 결정 채널에 소유자의 명시적 승인과 범위가 있고 현재 작업이 해당됨 | 제품이 Slack이라는 이유로 배제하지 않는다. 조건이 맞는 결정만 사용한다. |
| 공식 문서 두 개가 충돌하거나 필수 원문을 읽을 수 없음 | AI가 임의로 정하지 않는다. 의존하는 판단과 필요한 소유자 확인을 명시하고 독립 작업은 계속한다. |
| 승인 후 공식 규칙이 대체됨 / 관련 없는 문구만 바뀜 | 각각 영향받는 계획 재승인 / 영향 없음 근거 기록으로 구별한다. |
| 출처 미등록 로컬 작업 또는 기존 버전에 고정된 티켓 | 신규 외부 연결·상태 필드·소급 승인 없이 기존 경로로 진행한다. |
| 원문은 읽을 수 있지만 저장소 독자에게 공유할 수 없음 | 제한된 내용·식별자를 계획, 로그, 하위 작업에 복제하지 않는다. |
| 동일한 Go API 변경을 SDLC와 `go-backend` 단독으로 각각 요청 | 두 경로에서 동일한 승인 규칙·판본을 식별하고 같은 계약에 반영한다. 하위 `api-contract`가 같은 출처를 다시 검색하지 않으며, 단독 실행은 SDLC 상태를 만들지 않는다. |
| 같은 코드를 `code-review`로 단독 검토 / 프로젝트와 무관한 공개 API 사용법만 질문 | 검토는 적용 표준 위반을 식별한다. 공개 문서 설명은 사내 출처를 열지 않는다. |

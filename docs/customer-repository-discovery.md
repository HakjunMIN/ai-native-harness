이 문서는 `ai-native-sdlc`를 실제 고객 저장소에 적용하기 전에 **누구에게 무엇을
질문하고, 어떤 증거와 산출물을 확보하며, 어떤 도구·개발 절차·승인 체계를
연결해야 하는지** 정리한 인터뷰 및 도입 평가 가이드다.

아래 질문과 양식은 탐색용이다. 고객 환경의 확인 결과나 도입 승인 기록이 아니며,
이 문서를 작성했다고 고객 리포 설치·수정·외부 서비스 접근이 허가되는 것은 아니다.
고객별 탐색 산출물의 보관 위치와 접근 권한은 먼저 합의하고, 고객 정보는 이 하네스
공개 저장소에 기록하지 않는다.

## 1. 먼저 확인할 적용 범위

현재 하네스의 기본 대상은 **Grafana datasource/panel/app + React/TypeScript →
Spring Boot BFF(Gradle) → SigNoz query-service** 모노레포다.
BFF의 ClickHouse 직접 접근과 SigNoz 자체 UI 노출을 기본 설계로 삼지 않는다.
ClickStack/HyperDX는 명시적인 대안 평가 또는 기존 사용 환경에만 해당한다.

| 구분 | 탐색할 내용 | 판단 |
|---|---|---|
| 공통 개발 원칙 | AC 기반 요구사항, 위험 분류, 독립 리뷰, 증거 기반 검증, 사람 승인 | 고객 프로세스에 매핑할 수 있는지 확인 |
| 저장소별 설정 | 실제 모듈 경로, 실행 명령, 허용 모델, Jira 매핑, 운영 경로 | `sdlc-setup`과 설정 파일로 연결할 항목 |
| 기술 스택 의존 | Grafana, Spring/Gradle, SigNoz, 프런트엔드 Gherkin, Helm/ArgoCD | 다른 스택이라면 관련 스킬·검증·릴리스 계약의 적응 범위를 별도 산정 |
| 실행 환경 의존 | CLI, 로컬 에이전트, 모델 라우팅, 브라우저, 훅, 네트워크 | 파일 존재가 아니라 실제 고객 환경의 실행 증거로 확인 |
| 조직 통제 | 코드 외부 전송, 승인권자, 브랜치 보호, 배포 RBAC, 감사 | 프롬프트·훅으로 대신할 수 없는 통제 |

**다른 언어·멀티리포·다른 CI/CD로의 적용을 설정 변경만으로 완료할 수 있다고
가정하지 않는다.** 특히 현재 릴리스 게이트는 exact-SHA CI, immutable digest,
ArgoCD `Synced`/`Healthy` 등의 증거를 기대한다. 비컨테이너·비ArgoCD 환경은
스킬뿐 아니라 상태 검증 계약과 테스트의 변경 필요성도 평가해야 한다.

탐색 결과는 다음 중 하나로 제안한다. 이는 이 가이드의 도입 판단이지 하네스의
`state.json` 상태값이 아니다.

- **파일럿 진행:** 필요한 권한·증거·검증 환경이 확보되고 기존 계약에 부합한다.
- **적응 작업 후 진행:** 스택/프로세스 차이를 해소할 범위·담당자·승인 기준이 합의됐다.
- **보류:** 데이터 처리 승인, 필수 검증, 승인권자 또는 운영 권한 분리가 해결되지 않았다.

## 2. 인터뷰 전에 받을 자료

처음에는 승인된 읽기 전용 자료만 요청한다. 운영 자격증명, 고객 원본 데이터,
비밀정보가 포함된 로그를 수집하지 않는다.

| 자료 | 확인 목적 | 우선 제공 형태 |
|---|---|---|
| 리포 목록·소유 팀·기본 브랜치 | 적용 단위와 책임 경계 | 접근 가능한 URL/식별자, 담당 역할 |
| `AGENTS.md`, 개발 가이드, ADR, 아키텍처 그림 | 기존 규칙·설계 의도·에이전트 지침 충돌 | 승인된 문서 링크 |
| manifests, lockfiles, Gradle wrapper/settings, plugin 설정 | 실제 스택·버전·빌드 단위 | 해당 파일 경로와 기준 commit SHA |
| CI 정의·최근 성공/실패 결과·브랜치 보호 | 필수 체크와 현재 실패 기준선 | 비식별 실행 링크 및 설정 증거 |
| 대표 요청·버그·PR·리뷰 사례 | 실제 업무 흐름과 승인 관행 | 단순 변경·복합 변경·긴급 수정 사례 |
| API 계약·데이터 흐름·인증/테넌트 설계 | 연동 경계와 고위험 변경 영역 | OpenAPI, 흐름도, 비식별 예시 |
| 테스트 목록·fixture·개발 환경 시작 방법 | 재현 가능성과 검증 공백 | 명령, 필요한 서비스, 합성 데이터 |
| GitOps/배포·롤백·장애 대응 문서 | 소스에서 운영까지 추적 | 환경별 경로, 승인 흐름, runbook |
| AI/보안/개인정보/라이선스 정책 | 사용 가능한 모델·도구·데이터 | 정책 링크, 담당 부서의 승인 조건 |
| 현재 리드타임·리뷰 대기·결함 지표 | 도입 전후 비교 기준선 | 산식·기간·표본 수가 있는 집계 |

자료가 없으면 “없음”, 접근이 불가능하면 “접근 차단”, 사실 확인이 안 됐으면
“미확인”으로 구분한다. 인터뷰 응답만으로 명령 실행이나 권한 검증을 완료 처리하지 않는다.

있지만 요구·계획·운영 승인권자는 명시적으로 지정한다. 모든 질문의 답을 받을 필요는
없어도, 해당 파일럿의 권한과 정확성에 영향을 주는 미해결 질문은 남기지 않아야 한다.

### 인터뷰에서 반드시 구체화할 질문

**요구사항과 완료:** “검색이 빨라져야 한다” 대신 어떤 사용자·데이터 규모·측정
환경·응답시간 기준인지 확인한다. “테스트 통과” 대신 어떤 AC가 어떤 검사에서
확인되는지 묻는다. “완료”가 개발 완료, 릴리스 준비, 운영 반영 중 무엇인지 분리한다.

**권한과 예외:** 긴급 수정에도 유지할 승인·검증은 무엇인지 확인한다. 자동화가
차단되면 승인 절차를 변경할지, 필요한 환경을 복구할지 결정할 담당자를 정한다.
미확인 위험을 light로 낮추거나 필수 검사를 N/A로 바꾸는 우회는 허용하지 않는다.

**독립 리뷰:** 작성자와 다른 세션의 리뷰가 가능한지, 사람이 리뷰할 경우 정책상
허용되는지 확인한다. 다른 모델 계열은 신규 정책에서 권고이지 기본 필수는 아니다.
명시적으로 `requireDifferentFamily: true`를 택하면 실제 교차 계열 라우팅이 필요하고
인간 리뷰로 대체할 수 없다.

### 인터뷰 기록 양식

```markdown
# I-XX 인터뷰 기록
- 일시 / 참여 역할:
- 대상 저장소 / 기준 revision:
- 확인한 사실과 근거 링크:
- 질문과 응답:
- 결정한 사항 / 결정 권한을 가진 역할:
- 가정과 검증 방법:
- 미해결 질문 / 영향받는 작업 / 담당 역할 / 답변 기한:
- 후속 조치:
- 비식별화 및 공유 범위:
```

응답과 관찰 사실, 진행자의 추론을 구분한다. 인터뷰 참여나 회의록 확인은
특정 요구·계획·운영 변경의 G1/G2/G5b 승인을 대신하지 않는다.

## 4. 저장소·환경 탐색 체크리스트

| 영역 | 실제 확인할 내용 | 결과에 포함할 근거 |
|---|---|---|
| 구조 | 모노레포/멀티리포, 모듈, 담당 팀, 서브모듈, 생성물, 수정 금지 경로 | 경로·소유자·의존성 맵 |
| 도메인/데이터 | 용어 충돌, API, 인증, 테넌트 격리, 데이터 등급, 보존 | 경계와 금지 흐름, 합성 fixture |
| 스택 | Java/Node/Grafana/SigNoz 실제 버전, wrapper/lockfile, 업스트림 패치 | 파일 경로와 revision; 예시 버전 사용 금지 |
| 개발 환경 | OS/컨테이너, 네트워크·프록시·인증서, 오프라인 제약, 외부 서비스 | 재현 절차와 실행 실패 원인 |
| 테스트 | unit/integration/API/BDD/E2E, 접근성, 시각 회귀, 성능·부하 | 정확한 명령·실행 시간·결과·환경 |
| Git/CI | 브랜치 전략, commit/push/merge 허가, 필수 체크, CI SHA, 보호 설정 | 실제 설정과 대표 PR |
| 에이전트 환경 | 로컬 스킬 충돌, 역할 발견, 모델, 도구 권한, 브라우저, 훅 | 실제 실행/차단 증거와 미검증 기능 |
| 병렬 작업 | worktree 허용 위치, 공통 계약, 파일 소유, 상태 단일 작성자 | 순차/병렬 판단과 승인된 경로 |
| 릴리스 | 환경별 설정, production 경로, artifact digest, GitOps 앱, rollback | 소스·이미지·배포 revision 연결 |
| 운영/비용 | SLO, smoke, 알림·당번, CLI/모델 사용량, 테스트 인프라 비용 | 기준선, 예산 한도, 운영 책임 |

기본 worktree 도구는 저장소 옆 `<repo>.sdlc-worktrees/`를 사용한다.
고객 정책이 저장소 밖 쓰기를 금지하면 이 동작을 사전 승인받거나, 범위가 허용되는
단일 checkout 순차 작업을 택한다. 경로만 다르다고 공유 계약 변경을 병렬화하지 않는다.

## 5. 도구 목록과 사용 조건

아래는 설치 지시가 아니라 **기존 도구를 재사용하기 위한 인벤토리**다.
필수 여부는 선택한 작업에 따른다. 새로운 MCP·플러그인·의존성을 탐색 명목으로
자동 설치하지 않으며, 인증정보는 문서나 `ai-native-sdlc.config.json`에 저장하지 않는다.

| 범주 / 도구 | 적용 조건과 역할 | 확인할 권한·증거 |
|---|---|---|
| Git, Bash, curl | 설치·소스·변경 관리. curl은 원격 다운로드 방식에서 사용 | 승인된 소스/ref, 파일 충돌, 네트워크; 스크립트 사전 검토 |
| Node.js 22+ | 설치 후 하네스 스크립트·훅 실행 | 대상 환경 버전과 실제 스크립트 실행 |
| Copilot CLI / Claude Code / Codex | 선택한 로컬 실행 호스트. 모두 도입할 필요는 없음 | 조직 사용 승인, 실제 역할/스킬/훅 로딩, 라이선스·인증 |
| 승인된 모델과 로컬 서브에이전트 | 작성·검증·독립 리뷰 | 실제 모델 ID/계열·세션·라우팅·역할별 도구 |
| GitHub UI/API 또는 기존 CLI | PR, 보호 규칙, 필수 CI, 승인 근거 조회 | 최소 권한; 읽기와 게시/머지 권한 분리 |
| Atlassian Rovo MCP | Jira 경로를 사용할 때만 요청 조회·동기화·발행 | 승인된 읽기/쓰기, 프로젝트/전이/관계 ID; 탐색용 이슈 생성 금지 |
| Gradle wrapper, JDK, JUnit 및 기존 통합 테스트 도구 | Spring BFF 빌드·단위·통합·API 검증 | 실제 task 구분, DB/서비스 fixture, 재현 가능한 결과 |
| 저장소의 JS 패키지 관리자, TypeScript, lint, Jest/RTL | FE 정적·컴포넌트 검사 | lockfile과 실제 scripts; 임의 도구 교체 금지 |
| Gherkin 생성 도구, Playwright, axe, 스크린샷 도구 | 해당 FE 동작·E2E·접근성·시각 검사 | 브라우저와 테스트 환경, 기준 이미지 승인 |
| Grafana 개발 샌드박스, 실제 `@grafana/ui` | Grafana UI/플러그인 변경 시 | 합성 데이터, 테마·상태·키보드 검증 |
| Docker/기존 컨테이너 도구 | 기존 개발·통합 환경이 요구할 때만 | 로컬 실행 권한, 이미지 출처, 자원·네트워크 |
| SigNoz/query-service, OTel, ClickHouse 관련 관측 도구 | 해당 스택의 연동·관측성 작업 | 버전·배포 구성·비식별 telemetry; BFF 경계 유지 |
| GitHub Actions, 이미지 레지스트리 | 현재 릴리스 계약의 CI/artifact 추적 | PR head SHA의 필수 체크, immutable digest |
| Helm, ArgoCD, Kubernetes 조회 도구 | 해당 배포 경로의 검증·관측 | 승인된 read-only 조회, 차트 검증, prod RBAC |
| 고객의 비밀정보 관리·SAST·의존성/라이선스 검사 | 조직 정책 또는 변경 위험이 요구할 때 | 기존 CI와 결과 재사용, 토큰 원문 수집 금지 |
| ClickStack/HyperDX | 명시적 평가 또는 기존 사용 범위에 한정 | 별도 평가 목표·비용·승인; 필수 도구 아님 |

프런트엔드 관찰 가능 동작은 AC에 연결한 Gherkin/E2E로, 백엔드는 API 예시와
JUnit 기반 검증으로 연결한다. 백엔드 검증을 위해 Cucumber 도입을 기본 요구하지 않는다.

### 도구/명령 등록 양식

| 항목 | 기록할 값 |
|---|---|
| 식별 | 도구/검사명, 목적, 대상 모듈, 담당 역할 |
| 실행 | 실제 버전, 저장소 상대 `cwd`, 정확한 `argv`, 필요한 환경 |
| 접근 | 읽기/쓰기/실행 범위, 승인 역할, 자격증명 공급 방식의 식별자만 |
| 데이터 | 입력 데이터 등급, 외부 전송 대상, 로그 비식별화·보존 규칙 |
| 증거 | 확인 일시, source SHA, 종료 코드, 출력/리포트 위치 |
| 판정 | 확인됨 / 미확인 / BLOCKED / N/A와 사유, 영향받는 검사 |

하네스 `commands`에는 `{cwd, argv, purpose}` 레코드를 사용한다. 다른 인벤토리
필드를 임의로 설정 스키마에 추가하지 않는다. `models`는 실제 사용 가능한 ID만
설정하고, 설정 파일 작성 자체를 런타임 라우팅 성공으로 간주하지 않는다.

## 6. 산출물 형태

### 6.1 고객 도입 탐색 패키지

다음은 **권장 보관 구조이며 하네스가 자동 생성하는 파일이 아니다.**
고객 승인 저장소 또는 접근 제한 문서 공간에 보관한다. 기밀 원본 대신 승인된
참조와 비식별 요약을 사용하고, 공개 저장소와 고객 문서를 분리한다.

```text
<고객이 승인한 탐색 문서 위치>/
  00-scope.md                    # 목적, 적용/제외 범위, 담당 역할
  01-interviews.md               # 질문·응답·근거·미해결 항목
  02-repository-map.md           # 모듈·도메인·데이터·소유권
  03-tooling-and-commands.md     # 도구·권한·명령·확인 증거
  04-process-and-approvals.md    # 현행/목표 프로세스와 승인 책임
  05-fit-gap-and-risks.md        # 차이, 위험, 적응 작업, 차단 요소
  06-pilot-plan.md               # 파일럿 AC·범위·측정·중단 조건
  07-readiness-decision.md       # 진행/적응 후 진행/보류와 결정 근거
```

| 산출물 | 최소 내용/형식 | 확인 책임 |
|---|---|---|
| 범위·목표 | Markdown; 대상 리포/모듈, 기대 결과, 비목표, 성공 기준 | 스폰서·제품 책임자 |
| 인터뷰/질문 대장 | 질문 ID, 응답, 근거, 미확인, 담당 역할, 기한 | 각 응답 책임자 |
| 저장소/도메인 맵 | 경로·소유자 표 + 필요 시 Mermaid/C4 + 계약 참조 | 테크리드·도메인 담당 |
| 도구·명령 카탈로그 | 명령 등록 표, 실행 증거, 권한·데이터 조건 | 개발·플랫폼·보안 |
| 프로세스·승인표 | 현행→목표 매핑, 게이트별 승인 역할과 대체자 | 개발 책임자·운영 책임자 |
| Fit-gap·위험 대장 | 차이, 영향, 설정/코드/조직 개선 구분, 담당·기한·완료 증거 | 테크리드·관련 통제 책임자 |
| 파일럿 계획 | 실제 요청/AC, 검사, 인수 조건, 표본·측정법·중단 조건 | 제품·QA·개발 책임자 |
| 준비도 결정 | 근거 링크, 남은 제한, 결정 역할·일시, 재평가 조건 | 고객의 도입 결정권자 |

설치 후에는 실제 고객 리포의 `ai-native-sdlc.config.json`에 모듈·명령·모델·
capabilities·Jira·release 매핑을 연결한다. 기존 설정이 있으면 덮어쓰지 않고
diff로 검토한다. 기존 `AGENTS.md`와 관리 파일·훅의 충돌도 변경 제안에 포함한다.

### 6.2 개별 개발 작업의 정규 산출물

도입 탐색 패키지와 개별 작업의 게이트 증거는 별개다. 실제 SDLC 작업은 현재 v1의
`docs/sdlc/<ID>/`를 사용한다. Jira 키 또는 `local-<slug>`를 ID로 사용하며,
로컬 요청서 변경은 기존 `intake.md` 덮어쓰기가 아니라 새 ID로 시작한다.

| 단계 | 정규 산출물 | 중요한 내용 |
|---|---|---|
| 접수/Discovery | `intake.md`(로컬) 또는 Jira snapshot, `01-discovery.md`, `state.json` | 불변 요청 근거, AC ID, 모듈 맵, 범위/위험/질문 |
| 요구 구체화 | 해당 시 `features/*.feature`, 프로토타입 증거 | FE 관찰 동작, UI 상태·접근성; 선택과 승인은 별개 |
| Plan | `02-plan.md`, 해당 시 ADR/`openapi.yaml`, 테스트 매트릭스 | 대안·계약·AC별 검사·릴리스/복구 |
| sub task 정의 | draft와 `plans/<revision>/tasks.json`, strict의 생성 상세 뷰 | `tasks.mjs prepare`로 정규 manifest 생성; AC 중복 수동 관리 금지 |
| Implement | `03-impl-log.md`, sub task별 실행·리뷰 증거 | 행동 변경 RED/GREEN, 리팩터링 before/GREEN, 문서/설정의 관련 검사 |
| Verify | `04-verify-report.md`, 실행 로그·UX·독립 리뷰 증거 | AC별 판정, 명령/cwd/종료 코드/시간, SHA, hash, 미검증 범위 |
| Release | `05-release.md`, `production-proposal/` | CI SHA, digest, 환경별 상태, 사람 승인, smoke/rollback 근거 |

게이트 증거는 실제 파일의 `{path, sha256}` 참조로 연결하고, G3 이후는 검증한
소스 `subjectHead`에 연결한다. 소스 SHA, 이미지 digest, GitOps revision은 서로
다른 값이다. 샘플 문서·빈 리포트·이전 실행 로그를 실제 성공 증거로 쓰지 않는다.

### 6.3 프로젝트 공통 기준과 기능별 결정

프로젝트 표준은 현재 지켜야 할 규칙이고, ADR은 그 규칙이나 구조를 선택한
이유와 대안·결과의 기록이다. 여러 기능에 영향을 주는 결정은 프로젝트 차원에서
관리하고, 기능 작업은 공통 기준을 참조한다. 첫 기능에서 나온 결정이라도 인증,
테넌트, 공유 API, 데이터 소유권에 영향을 주면 프로젝트 ADR로 분류한다.

기존 고객 문서 위치가 있으면 우선 사용한다. 없을 때의 기본 구조는 다음과 같다.
설치기가 이 문서들을 자동 생성하지는 않으며, Setup과 해당 작업에서 필요한
문서만 작성한다. 고객의 기준은 고객 프로젝트에 두고 설치된 하네스 내부에는 두지 않는다.

```text
AGENTS.md                         # 실제 문서 위치와 읽기 규칙
docs/
  architecture/
    overview.md                   # 현재 시스템 경계와 의존성
    adr/
      README.md                   # 결정 목록, 상태, 범위, 담당자
      ADR-0001-<decision>.md       # 공통 결정의 근거와 승인 기록
  standards/
    README.md                     # 표준 목록, 적용 범위, 담당자
    <topic>.md                    # 현재 규칙, 검증 방법, 근거 ADR
  sdlc/
    <ID>/
      02-plan.md                  # 공통 기준 참조와 기능 설계
      adr/<feature-decision>.md   # 필요한 경우에만 기능 한정 결정
```

| 단계 | 공통 기준과의 연결 |
|---|---|
| Setup | 기존 문서·소유자 확인, 프로젝트 AGENTS.md에 실제 위치와 읽기 규칙 기록 |
| Discovery | 적용 표준·ADR, 충돌, 예외, 프로젝트 차원의 신규 결정 식별 |
| Plan | Project baseline에 문서 경로·절·기준 commit·상태·담당자·예외 기록 |
| Implement | 승인된 기준과 수정 범위 준수, 공통 문서 변경 시 영향 확인 |
| Review/Verify | 표준 준수, 기준 이후 변경, 공통 변경 승인과 예외 만료 검증 |
| Release/Handoff | 공통 결정 변경, 마이그레이션 의무, 예외 종료 조건과 담당자 인계 |

표준 원문은 기능별 계획에 복사하지 않는다. 미커밋 문서는 HEAD에 포함된 것으로
기록하지 않고 실제 내용 SHA256과 미커밋 상태를 남긴다. 적용 문서가 없으면
없다고 기록하며, 빈 표준이나 승인되지 않은 정책을 만들어 완료 처리하지 않는다.

공통 변경과 예외는 해당 프로젝트·영역 소유자의 명시적 승인이 필요하다.
기능 G2 승인이 자동으로 공통 정책 변경을 승인하지는 않는다. 예외에는 규칙,
사유, 범위, 위험, 보완 검증, 담당자, 만료 또는 종료 조건과 승인 근거를 기록한다.
채택된 결정을 바꾸면 새 ADR을 만들고 이전 ADR과 `superseded` 관계를 연결하며,
현재 표준과 인덱스도 함께 갱신한다. 기능 결정의 공통 승격 시 원래 작업을 참조하되
종료된 작업의 해시 증거를 수정하거나 과거 기록을 이동하지 않는다.

현재 상태 검증기는 프로젝트 공통 문서의 변경을 자동 추적하지 않는다.
기준 비교 결과는 작업 내부 계획·리뷰 보고서에 남겨 기존 게이트 증거로 연결한다.
상위 경로 참조나 심볼릭 링크로 증거 경계를 우회하지 않는다. 기존 승인 작업에
기준 기록이 없으면 별도 작업 내 보고서로 비교와 제한을 남긴다. 요구·계획에
실질적 영향이 있으면 G1/G2부터 재승인하고, 무관한 변경은 사유를 기록한다.

세부 승인·승격·기준 비교 규칙은
[프로젝트 거버넌스](../skills/sdlc/references/project-governance.md)를 따른다.

## 7. 고객 개발 프로세스와 연결

### 7.1 도입 진행 순서

| 순서 | 수행 내용 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 1. 접근·데이터 합의 | 대상/비대상 리포, 읽기 권한, 모델 입력 데이터, 문서 보관 합의 | 고객의 조사 허가와 데이터 처리 범위 확인 |
| 2. 인터뷰·현행 파악 | 위 질문과 실제 파일/사례를 대조 | 사실·가정·차단 항목이 구분됨 |
| 3. 적합성·기준선 | 빌드/테스트·도구 capability를 승인 범위에서 확인 | 현재 실패와 하네스 적응 작업이 구분됨 |
| 4. 파일럿 합의·설정 | 파일럿 선정, 도구/정책 승인, 설치 diff 검토, `sdlc-setup` | 필수 capability·명령·승인권자 확보 |
| 5. 제한된 실행 | 승인된 한 작업을 Discovery부터 검증·인계까지 진행 | 실제 증거와 제한을 보존; 운영 변경은 사람이 수행 |
| 6. 회고·확대 결정 | 기준선 비교, 실패·수작업·비용 분석 | 확대/보완/중단 결정 및 유지보수 책임 합의 |

### 7.2 작업별 게이트와 책임

| 게이트 | 고객 프로세스에 대응할 시점 | 요구되는 증거/결정 | 책임 |
|---|---|---|---|
| G0 | 요청 접수·분석 준비 | 요청 원문 근거, AC, 모듈 맵 | Discovery 담당 |
| G1 | 요구사항 확정 | 범위·AC·UI/BE/FE 결정의 실제 승인 | 지정된 사람 |
| G2 | 설계·계획 확정 | 계획, 정책, 정규 sub task manifest, 계약/검사, strict 계획 리뷰 | 지정된 사람 |
| G3 | 구현 및 통합 완료 | sub task별 검증, 독립 리뷰, 통합 검사, 소스 SHA | 구현 진행 담당 |
| G4 | 릴리스 준비 검증 | 최신 AC 검사와 spec/standards/security 검토, 해당 UX 증거 | 검증 담당·독립 리뷰어 |
| G5a | dev/staging 확인 | 현재 SHA의 필수 CI, digest, 사람이 수행한 프로모션과 health | 릴리스 담당 |
| G5b | 운영 반영 확인 | 사람의 승인/머지 근거, 관측한 digest·Synced/Healthy·smoke | 지정된 사람·운영자 |

승인에는 대상 산출물·버전과 실제 승인 참조·시각을 남긴다. 에이전트가 기록한
JSON만으로 승인자 신원이 인증되는 것은 아니므로 고객의 PR/감사 체계를 연결한다.
사람 게이트는 생략하거나 N/A 처리하지 않는다.

**Light/strict:** 저위험·단일 결과의 bounded 작업은 light로, 아키텍처·고위험·
다중 결과는 strict로 분류한다. Light는 테스트/구현 작성자 통합과 독립 combined
리뷰를 허용한다. Strict는 테스트 작성/구현 역할 분리와 계획·최종 독립 리뷰,
spec/standards 축을 유지한다. 두 방식 모두 사람 승인과 필수 검증은 유지한다.

**Jira/로컬:** Jira strict는 G2 승인 후 자식 티켓 발행과 원격 반영 확인을 거쳐
구현한다. Jira light는 부모 이슈를 사용한다. 로컬 작업은 Jira·MCP·자식 발행이
필요 없지만 동일한 승인·검증 기준을 따른다. 다른 이슈 도구의 자동 연동을 지원한다고
가정하지 말고 로컬 경로 또는 별도 적응 작업으로 평가한다.

**변경/재개:** 요구 변경은 G1, 계획·정책·계약 변경은 G2, 코드 변경은 G3부터
하류 증거를 무효화하고 재검증한다. 승인 정책은 설정 파일 수정만으로 바뀌지 않는다.
재개 시 상태·증거·작업 브랜치를 대조하고, 실패한 필수 검사를 통과로 바꾸지 않는다.

**릴리스/종료:** v1 훅은 `git push`·`gh pr merge`와 직접 배포 변경을 보수적으로 차단한다.
로컬 merge의 중립 응답은 실행 허가가 아니며, 사용자 허가를 받은 컨덕터의 소스
통합에만 사용한다. 브랜치 게시·프로모션 머지는 사람이 실행한다.
릴리스 작업자는 운영 제안만 작성하며 실제
prod desired-state 수정·머지·sync는 하지 않는다. 운영 미반영 파일럿은 “G4까지 검증,
릴리스 미완료”처럼 보고하고 G5b/Jira Done을 꾸미지 않는다. 승인된 연구용 spike의
`spike-complete`는 구현/배포 완료와 별개의 연구 결과다.

## 8. 파일럿 설계와 도입 판단

첫 파일럿은 **고객에게 가치가 있고, AC가 분명하며, 되돌릴 수 있는 작은 수직 변경**을
우선한다. 초기 후보로 인증/테넌트 구조 변경, 파괴적 DB 이전, 핵심 운영 배포 자동화는
피한다. UI 파일럿이면 관련 UX 검증까지, 백엔드 파일럿이면 해당 API/통합 검증까지 포함한다.
작은 파일럿의 성공을 다른 스택·권한·고위험 업무의 성공으로 일반화하지 않는다.

### 파일럿 계획에 채울 항목

| 항목 | 합의할 내용 |
|---|---|
| 문제·범위 | 요청 원문, 사용자 결과, AC ID, 대상 모듈, 비목표 |
| 정책·책임 | 위험 분류, light/strict 근거, 작성/리뷰/승인/운영 역할 |
| 검증 | AC별 검사와 환경, 실제 연동/mock 구분, 현재 기준선 실패 |
| 실행 한도 | 허용 경로·도구·데이터·외부 쓰기·모델, 시간/비용 상한 |
| 종료 지점 | G4까지인지 실제 릴리스까지인지, 종료 후 유지보수 담당 |
| 복구·중단 | 실패 시 변경 보존/복구 절차, 연락 역할, 재개 승인 |
| 판정 | 지표의 기준선·목표·허용 회귀·표본·기간, 최종 결정권자 |

### 측정할 지표

목표 수치는 고객 기준선과 위험에 맞춰 **시작 전에** 정한다. 개선율을 미리 보장하지
않고, 작은 표본의 결과는 관찰값으로 보고한다.

| 지표 | 측정 방법 |
|---|---|
| 흐름 시간 | 접수→G1→G2→G4→배포 시간을 분리하고 승인 대기와 실제 작업 시간을 구분 |
| 품질 | AC 충족/미검증 수, 리뷰 발견·재작업 수, 릴리스 후 결함을 같은 기준으로 비교 |
| 증거 완결성 | 필수 검사·리뷰·승인 중 현재 revision에 연결된 유효 증거의 비율 |
| 안정성 | 첫 실행 실패, flaky 재실행, capability 차단, 수동 개입 원인과 횟수 |
| 비용 | 모델/CLI 사용량·라이선스, CI/환경 자원, 사람의 검토·운영 시간을 구분 |
| 운영 결과 | 실제 배포했다면 smoke·SLO·롤백 여부; 미배포면 측정하지 않았다고 명시 |

### 즉시 중단하거나 해당 작업을 차단할 조건

- 허용되지 않은 데이터 전송, 권한 밖 저장소/파일 변경 또는 운영 변경 시도.
- 필수 테스트·독립 리뷰·사람 승인의 부재, 증거와 현재 SHA/hash의 불일치.
- 해결되지 않은 인증/테넌트/파괴적 변경 위험, 승인 범위를 넘어선 구현.
- 합의한 예산·시간 한도 초과 또는 재현 불가능한 반복 실패.

중단 시 진행 변경과 증거를 보존하고 담당자·영향·재개 조건을 기록한다. 연동 장애는
의존하는 작업만 차단하며, 다른 승인된 작업까지 무조건 중단하지 않는다. 데이터/권한
침해 의심은 고객의 사고 대응 절차를 따른다.

## 9. 최종 준비도 회의 체크리스트

- [ ] 고객 목표·파일럿 AC·비목표·판정 기준과 기준선이 합의됐다.
- [ ] 저장소·데이터 접근과 모델/도구 사용이 승인됐다.
- [ ] 실제 모듈·명령·환경이 확인됐고 필수 검증 차단이 해결됐다.
- [ ] 스택/CI/CD 차이가 설정으로 해결되는지, 하네스 코드 적응이 필요한지 구분됐다.
- [ ] 스킬·에이전트·훅의 실제 동작과 호스트별 미검증 제한을 기록했다.
- [ ] G1/G2/G5b 승인 역할, 독립 리뷰 방식, 운영 실행자가 정해졌다.
- [ ] 브랜치 보호·필수 CI·prod RBAC 등 외부 통제가 확인됐다.
- [ ] 산출물 보관·접근·비식별화·보존/삭제 책임이 정해졌다.
- [ ] 설치/업데이트 출처와 버전, 변경 검토, 충돌 해결·되돌리기 절차가 합의됐다.
- [ ] 하네스/설정/스킬의 유지보수 담당과 정책 변경 시 재승인 절차가 정해졌다.
- [ ] 미해결 항목마다 담당·기한·차단 범위·재개 조건이 있다.
- [ ] 고객 결정권자가 진행/적응 후 진행/보류와 근거를 기록했다.

훅은 보안 샌드박스가 아니며, 도입 준비도 결정은 개별 작업의 G1/G2/G5b 승인이 아니다.
